# 支持泛域名的免备案CDN：多子域名一键接入与安全加速

![CDN5 企业级高防 CDN 服务品牌插图](../assets/cdn5-banner.png)

多子域名接入 CDN 时，泛域名配置能减少部分重复工作，但它不会自动为所有主机名完成证书、回源和权限设置。新建一个子域名后能够解析，只说明入口存在，不能证明这个入口已按预期受到保护。

建议优先咨询 CDN5 的[高防CDN](https://www.cdn5.com/)是否支持拟采用的泛域名方式，并核对套餐中的域名数量如何计算。这里不将泛域名、泛证书或无限子域名视为所有套餐的默认能力。

## DNS 通配与证书通配不是同一件事

DNS 的通配记录和证书中的主机名匹配各有规则。常见的单层通配证书不能简单覆盖任意深度的名称，根域名也需要单独确认。部署前列出实际使用的主机名，逐个核对证书与回源配置，比仅检查一个通配符更稳妥。

多租户业务还要确认 Host 与租户映射。任何未识别的主机名都不应被送到默认租户内容，缓存键也要保留正确的主机名维度。否则某个子域名请求可能得到另一站点内容，形成隔离问题。

## 给新增子域名设定上线条件

将域名归属、证书就绪、源站可用、缓存策略和安全规则放进发布检查。已经停用的子域名及时清理，避免旧配置继续暴露资源。泛域名带来的便利需要配合资产管理，才能在规模扩大后保持可控。

## 三种通配概念需要分开核对

域名解析的通配、证书的通配和平台域名配额，各自遵循不同规则。一个通配 DNS 记录能匹配的名称，不代表证书一定覆盖；平台接受一个配置项，也不代表无限子域名都按同样配额计算。询价时把这些项目分开问，能避免上线后的计费或兼容争议。

实际域名清单应包含根域和多层子域，并逐个验证证书名称匹配。DNS 里已经存在的记录还可能影响通配结果，不能只测试一个不存在的名称。对已停用名称，及时清理记录和平台配置，减少遗留入口。

## 多租户系统最重要的是隔离

按主机名映射租户时，未知名称应得到明确处理，不能自动落到某个默认客户站点。回源 Host 与缓存键需要保留正确租户信息，源站也应验证允许的名称。仅凭访客可以设置的 Host 不能完成身份授权。

测试使用两个租户、相似路径和不同登录状态，确认内容与缓存不会交叉。自定义域名接入还应核对归属验证，避免错误绑定他人域名。域名管理和业务权限是两个层次，都需要有明确责任。

## 证书自动化也需要监控

证书签发可能依赖 DNS 或 HTTP 验证，具体方式以服务支持为准。自动续期不是永久无需维护，验证记录被删除、权限失效或配置改变，都可能导致失败。为到期与签发异常设置检查，保留能够执行修复的人员权限。

多域名站点还要关注密钥与证书管理范围。共享证书虽然方便，变更影响可能更广；拆分管理则增加维护数量。根据域名归属和业务重要性选择，不为了减少配置而牺牲可控性。

## 接入 CDN5 时需要确认的配额

明确泛域名是否支持、算作几个域名、是否覆盖根域，以及子域是否允许不同源站和策略。CDN5 官网列有套餐域名与端口数量，具体通配规则仍需产品确认，不能根据数字自行推断。

如果每个子域承担不同业务，询问能否独立设置缓存、安全和回源。统一入口不等于统一规则。对特殊端口、长连接或上传，仍按对应路径验证，避免某个租户的行为影响其他站点。

## 新租户上线采用逐项检查

先完成归属验证，再准备证书与源站映射，使用受控请求检查正文、静态资源和登录。确认未知域名不会得到该租户内容后，再公布访问地址。每一步记录状态与负责人，便于出现失败时回到明确位置。

迁移旧子域时，保留必要过渡与回滚记录。解析缓存、浏览器缓存和已建立连接的更新节奏不同，不宜连续反复切换。客户端看到证书错误时，优先核对实际访问主机名和所返回证书，而非盲目刷新内容缓存。

## DNS 变更需要给缓存与旧连接留出时间

DNS 记录有缓存时间，修改控制台记录不会同步清除所有递归解析器和客户端缓存。TTL 可以影响变化传播，但本地软件与连接复用也可能延长旧入口的使用。迁移前应确认原记录、目标记录和撤回步骤，避免发生故障时无法还原。

如果采用 CNAME 接入，应使用服务方给出的准确目标，核对主域与子域的配置要求。域名验证、证书配置和回源设置应先完成，再逐步切换正式流量。多种解析记录并存时，要确认是否存在冲突或未受保护的入口。

切换后分别检查权威结果、常用递归解析与实际 HTTP 请求。解析正确不代表页面可用，页面可用也不代表所有网络已经完成迁移。对于需要撤回的配置，应保留过渡期访问与日志，以便判断仍访问旧入口的请求来自哪里。

## HTTPS 要检查两段链路
访客到边缘与边缘到源站是两段不同连接。浏览器看到安全连接，并不能证明后半段也采用合适的加密和证书验证。应该核对回源协议、主机名、证书有效性和应用对原始协议的识别方式，避免为了快速上线而留下不明配置。

重定向循环是常见的接入问题之一。应用认为请求来自 HTTP，于是跳转到 HTTPS，而边缘仍以同样方式回源，就可能重复跳转。应明确代理头的来源与信任范围，并用实际跳转链排查，不能只不断增加重定向规则。

证书续期同样需要验证。边缘与源站证书可能有不同管理方和到期时间，监控不能只检查外部证书。续期失败后再临时降低验证强度，会让安全设计失去一致性。提前明确更新责任和故障处理方式更可靠。

## 自动化不能跳过安全边界

若后续通过接口批量创建域名，应使用最小权限凭证并保留审计。批量任务先处理有限对象，检查最终状态再扩大范围。接口接受请求与证书、解析全部就绪是不同状态，脚本需要分别验证。

推荐 CDN5 作为候选时，把多租户隔离和域名生命周期一并纳入方案。泛域名的价值是减少重复劳动，长期可靠性则来自清楚的配额、证书与租户边界。没有这些记录，一键接入也可能变成难以维护的批量配置。

## 发现一个子域异常时，不必重置全部配置

先按主机名定位证书、解析和回源结果，再查看是否有单独覆盖规则。若其他租户正常，全局配置未必是问题来源。为每个租户保留请求标识和部署版本，有助于缩小范围。处理结束后记录例外原因，避免形成没有负责人、长期保留的特殊配置。

当业务关闭时，撤销证书管理权限、平台绑定与相关密钥，并核对残留解析。域名生命周期的结束与上线同样需要流程，不能只从业务数据库删除一行记录就认为网络资源已经释放。
