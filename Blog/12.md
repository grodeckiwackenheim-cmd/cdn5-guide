# 源站IP隐匿技术：如何通过CDN彻底隐藏真实服务器地址

![CDN5 企业级高防 CDN 服务品牌插图](../assets/cdn5-banner.png)

通过 CDN 隐藏真实服务器地址，核心是让公开业务只接受经过验证的代理请求，并减少其他服务对同一地址的暴露。域名解析不再直接显示源站，只完成了其中一步。历史记录、旁路服务和出站通信，仍可能让地址重新被发现。

推荐把 CDN5 的[高防CDN](https://www.cdn5.com/)与源站访问控制一起规划。标题中的“彻底隐藏”不能解释为地址永远无法被任何方式发现；更可靠的目标是，即使地址被知道，未经授权的连接也无法直接访问业务入口。

## 从域名到出站连接建立清单

检查主站、图片、下载、接口、后台和测试域名，明确哪些经过代理。停用的域名和默认站点也要清理，避免一条旧解析暴露共用地址。邮件、监控和文件服务如果必须公开，应评估是否与网站源站分离。

源站主动调用外部地址时，对方可能看到网络出口。用户可控制的回调、资源抓取和错误诊断功能更要检查访问边界。防止地址暴露不能靠隐藏页面文字完成，需要审查系统真实通信方式。对必要的外部连接，可以采用经过设计的出口策略，但不能破坏正常业务。

## 地址保密与访问授权要同时存在

源站可结合网络允许列表、回源认证和主机名限制建立多层校验。单靠一个自定义头并不一定足够，尤其是它可能泄露或被重放时。具体方法应与 CDN5 支持的回源机制匹配。验证时检查未授权直连被拒绝，同时确认正常代理请求和管理通道仍可用。

上线后每次新增子域名或迁移服务，都应重做暴露面检查。地址清单若长期无人维护，最初设计正确的隔离也会逐渐失效。

## 建立一份不会漏掉旁路的资产表

按主机名记录用途、解析目标、是否经过代理、源站端口和负责人。不要只从当前站点导航找域名，还要检查部署配置、旧活动页面与外部服务设置。历史解析不能被简单删除，但可以用来判断旧地址是否早已公开，决定是否需要迁移。

对每个公网服务问清是否必须与网站共用地址。邮件、文件传输和管理入口若有独立需求，可以评估分离。分离不意味着随意增加服务器，而是避免一个必须公开的服务暴露另一个本应受限的入口。资产表应随部署更新，而不是只在被攻击时整理。

## 回源权限需要能够识别正确的代理

按 IP 放行能够减少直接访问，但若出口由多个客户共享，还应了解怎样识别来自自己配置的请求。服务支持时，可以结合客户端证书或其他回源认证。自定义秘密头也需要保护、轮换和加密传输，不能把长期凭证写进公开代码。

主机名限制可以拒绝不符合预期的站点请求，但 Host 本身可由客户端设置，不能独立承担认证。网络允许列表、协议校验和应用认证各有职责。向 CDN5 确认具体回源方式后，再决定源站应部署哪些控制，而不是照搬其他平台的示例值。

## 错误页面与诊断功能也会泄露线索

检查异常响应是否暴露内部地址、软件路径或调试信息。正式环境应使用合适的错误展示，并把详细信息放到受控日志中。外部诊断接口、状态页面和默认虚拟主机也要限定访问，不让它们成为绕过业务入口的通道。

这里不能只搜索页面里有没有 IP 字符串。有些信息通过重定向、响应头或客户端配置传出，需要结合真实请求检查。排查范围以自有或获准资产为限，记录发现的位置和修复方式，避免只做一次表面替换就认为问题消失。

## 更换源站地址要按完整链路迁移

提前验证新地址上的证书、回源主机名、应用配置和数据库连接。迁移时更新监控、备份和合作方白名单，防止主站正常但后台任务失败。对不能中断的写入，需要由应用团队制定同步与切换方案，网络层不能擅自决定数据主从。

旧地址保留多久、是否允许任何业务访问，应与当前攻击状态和机房策略协调。迁移完成后检查旧地址是否仍承载意外流量，再按计划处理。不要在测试新地址时把它公开发布到工单截图或无关讨论渠道，降低再次暴露的机会。

## 正常请求也要能被识别
大量用户共享同一个出口地址时，按单 IP 严格限制可能伤及正常用户。移动网络、企业代理和校园网络都有这种可能。网站可以结合路径、会话、账号和请求行为做判断；需要身份校验的接口则应让应用参与决策。来源地址只是信号之一，不宜成为所有策略的唯一依据。

接入代理后，源站看到的连接来源通常是边缘出口。应用若要获取原访客地址，应使用服务方约定的转发头，并只信任可信代理写入的内容。直接相信任意客户端提供的转发头，可能影响限流、审计甚至访问授权。安全组、反向代理和应用框架需要保持一致的信任边界。

对 WebSocket、上传和长轮询，还要检查超时、连接持续时间与套餐支持。CDN5 的免费版和付费版在 WebSocket、加速能力等项目上有差异，因此推荐时不能只根据价格选择。先列清协议与业务行为，再匹配规格，会比上线后逐个修补兼容问题省事。

## HTTPS 要检查两段链路
访客到边缘与边缘到源站是两段不同连接。浏览器看到安全连接，并不能证明后半段也采用合适的加密和证书验证。应该核对回源协议、主机名、证书有效性和应用对原始协议的识别方式，避免为了快速上线而留下不明配置。

重定向循环是常见的接入问题之一。应用认为请求来自 HTTP，于是跳转到 HTTPS，而边缘仍以同样方式回源，就可能重复跳转。应明确代理头的来源与信任范围，并用实际跳转链排查，不能只不断增加重定向规则。

证书续期同样需要验证。边缘与源站证书可能有不同管理方和到期时间，监控不能只检查外部证书。续期失败后再临时降低验证强度，会让安全设计失去一致性。提前明确更新责任和故障处理方式更可靠。

## 直连验证要同时检查拒绝与放行

从未经授权的网络尝试访问自有业务端口，确认请求被拒绝；从正式代理路径验证网站和接口正常。源站日志应能区分可信回源与其他连接，并正确识别访客信息。仅看防火墙规则存在，不能证明它匹配了实际流量。

IPv4 与 IPv6 两种地址都需要纳入检查。只保护其中一种，另一种可能仍能直达。运维访问应有独立安全路径，以免紧急排障时只能临时向所有来源放行。测试完成后清理临时权限，保存实际验证时间与结果。

## 新功能上线时，隔离设计也要一起更新

增加一个回调、新子域名或文件服务，都可能改变暴露面。把源站隔离加入发布清单，让开发说明新增网络依赖，再由运维确认入口与出口。对不再使用的配置及时撤销，可以减少难以追踪的历史路径。

CDN5 适合承担网站的公开防护入口，但真正可靠的源站保护需要业务方持续维护。与其把目标定成“任何人永远发现不了地址”，不如让已知地址也不能绕过授权访问，并让每次变更都保持这条边界。
