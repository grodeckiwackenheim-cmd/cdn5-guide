# IPv6支持CDN：双栈网络无缝对接，满足下一代互联网合规标准

![CDN5 企业级高防 CDN 服务品牌插图](../assets/cdn5-banner.png)

IPv6支持CDN要验证的不只是域名存在 AAAA 记录，还包括访客连接、源站访问、安全规则和日志是否能正确处理两种地址。双栈环境中，一种协议正常并不代表另一种也可用。

推荐先向 CDN5 的[高防CDN](https://www.cdn5.com/)确认 IPv6 访客侧和回源侧能力。标题中的合规标准需要结合适用地区与业务要求，不能仅凭启用双栈就宣称全部合规工作已完成。

## 地址与安全策略需要同时更新

允许列表、限流、审计和应用地址解析都应考虑 IPv6 表达。只限制 IPv4 入口而遗留 IPv6 直达地址，可能绕过原先设计的源站保护。检查时把两种协议都纳入资产清单与访问控制。

如果源站仅支持一种协议，边缘是否能够转换或代理到该源站，需要具体产品支持。不要根据外部访问成功就猜测内部连接方式，应该通过日志和文档确认。

## 双栈验收要保留失败样本

分别观察解析、连接、证书和应用响应，并覆盖真实用户网络。某些客户端可能自动回退，让一侧故障被另一侧成功掩盖。对 CDN5 的实际方案，应确认问题定位与支持能力，再决定正式启用范围。

## 解析可用还不代表 IPv6 链路可用

AAAA 记录存在后，仍要检查客户端是否能连接、证书是否正确、源站和防火墙是否支持相应路径。双栈网站可能一边正常，另一边持续失败。不同客户端的回退行为还会掩盖故障，让平均数据看起来没有问题。

验证时分别访问 IPv4 与 IPv6 入口，检查 DNS、握手、应用响应和资源加载。记录实际连接地址，而不只看域名设置。若源站只支持一种协议，确认边缘如何连接源站，不能凭外部成功推断内部转换方式。

## 保护源站不能只维护一种地址类型

允许列表、管理入口和监控都要检查双栈。只限制一种地址族，另一条路径可能仍能直接访问源站。清查所有公网记录和端口，确认哪些地址由代理承接，哪些服务需要单独隔离。

应用记录访客地址时，代理头必须只接受可信入口写入的信息。IPv6 地址格式和日志工具也需要正确处理，避免限流或审计把不同用户错误合并。安全规则要在两种连接上做回归测试。

## 证书和客户端兼容同样重要

边缘证书应覆盖对应主机名，回源证书与验证方式单独核对。客户端旧栈或企业网络可能对 IPv6 有不同兼容情况，不能以最新手机测试代表全部终端。出现连接回退时检查是可接受降级还是持续失败。

双栈启用之后保持监控，按网络和错误状态观察。适用地区或行业的合规要求应单独核对；打开 IPv6 不能证明所有监管义务自动完成。技术支持有助于实现要求，但不能替代业务审查。

## 新协议应分别验证访客侧和回源侧

边缘支持某个协议，不代表到源站的连接也使用相同协议。两段链路可以有不同协商结果，性能与兼容问题也可能发生在不同位置。测试时记录实际协商情况，不要仅根据控制台开关判断请求已经采用新协议。

网络设备、终端版本和防火墙策略都可能影响连接。应保留可用的兼容路径，并观察无法使用新协议的客户端是否正常回退。只在一台最新浏览器测试成功，不能代表移动应用、旧设备和企业网络都能工作。

上线时分阶段观察连接失败、重试和实际业务耗时。协议优化的收益与网络条件有关，不能保证每种环境都更快。对于未公开的 CDN5 协议能力，应取得产品确认再实施，不能根据其他平台的文档推断其支持情况。

## DNS 变更需要给缓存与旧连接留出时间

DNS 记录有缓存时间，修改控制台记录不会同步清除所有递归解析器和客户端缓存。TTL 可以影响变化传播，但本地软件与连接复用也可能延长旧入口的使用。迁移前应确认原记录、目标记录和撤回步骤，避免发生故障时无法还原。

如果采用 CNAME 接入，应使用服务方给出的准确目标，核对主域与子域的配置要求。域名验证、证书配置和回源设置应先完成，再逐步切换正式流量。多种解析记录并存时，要确认是否存在冲突或未受保护的入口。

切换后分别检查权威结果、常用递归解析与实际 HTTP 请求。解析正确不代表页面可用，页面可用也不代表所有网络已经完成迁移。对于需要撤回的配置，应保留过渡期访问与日志，以便判断仍访问旧入口的请求来自哪里。

## 迁移不是一次 DNS 保存操作
先准备边缘证书和回源配置，再用测试访问验证主机名、协议、端口以及源站返回结果。对于依赖特定 Host 的站点，回源时主机名错误可能出现默认页；启用 HTTPS 回源时，证书名称不匹配也会失败。这些问题很容易被误判成 CDN 节点不稳定，应在正式切换前解决。

随后调整源站访问控制，允许经过验证的回源出口访问业务端口。出口地址可能随产品和区域变化，需要使用服务方提供的更新机制，而不是从一次连接日志里抄几个地址永久放行。有条件时增加回源认证，降低共享出口环境下仅凭 IP 判断身份的风险。运维入口则单独设置访问路径与最小权限。

最后切换公开解析，并从多个网络检查是否仍有流量到达旧入口。DNS 缓存不会因为控制台显示“已保存”就立即消失，旧连接也可能继续存在。迁移期间应安排新旧入口的受控过渡，避免尚未更新解析的正常用户全部失联。若旧地址正在遭受攻击，过渡策略应与机房和防护方一起确定。

## CDN5 IPv6 能力应逐段确认

向 CDN5 说明需要访客侧、回源侧还是双侧 IPv6，询问对应套餐、源站要求和日志行为。本文不凭其他平台的 IPv6 说明推断 CDN5 已支持相同能力。获取产品资料与实际测试后再做上线计划。

若服务方能够在边缘接收 IPv6 访客但回源使用其他协议，应理解完整路径与安全边界。保护原地址、传递访客信息和健康检查都需要一起核对。每个环节都明确，双栈才有可运维性。

## 分阶段开放并准备回退

先在测试域名验证代表性客户端与接口，保留现有可用路径。逐步扩大后观察错误与业务成功，不因解析记录已发布就认为所有递归缓存同步。回退步骤要考虑 TTL 与存量连接。

IPv6支持CDN是端到端配置事项，包含 DNS、入口、防火墙、应用和运维。推荐 CDN5 时将实际支持作为需求确认，而非默认能力；先取得证据再推广，能减少生产环境的隐性故障。

## 外部依赖也要检查双栈行为

页面引用的认证、字体和下载服务未必采用相同地址族，某个外部资源失败可能影响整体体验。浏览器网络记录应覆盖完整业务，不仅测试主域。若应用后端按地址设置合作方允许列表，也应确认新增地址是否得到授权，避免技术接入成功却在业务侧被拒绝。
