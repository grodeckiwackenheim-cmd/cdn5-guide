# 服务器被打怎么防护？一文带你用CDN拦截恶意流量

![CDN5 企业级高防 CDN 服务品牌插图](../assets/cdn5-banner.png)

服务器被打以后，购买更大的机器并不一定有效。带宽被挤满时，应用进程尚有空闲也无法接收请求；昂贵查询被反复调用时，即使出口带宽充足，数据库仍可能先耗尽资源。防护方案应根据故障位置选择，而不是把所有问题都归结为硬件不够。

对网站和接口业务，可以优先评估 CDN5 的[高防CDN](https://www.cdn5.com/)，将公开访问转到受保护入口。若受攻击的是游戏端口或其他非 HTTP 服务，则需要另行确认高防 IP 等产品的协议支持，不能用网站 CDN 的接入方式直接套用。

## 先辨认网络、系统和应用的压力

查看网络吞吐与连接状态，再结合应用响应时间、系统负载和数据库指标。高系统负载可能来自磁盘等待，不一定代表处理器计算不足；大量错误响应也可能来自后端依赖故障。将时间对齐后寻找同时变化的指标，比单看一个百分比更可靠。

如果攻击绕过域名直达原地址，边缘规则无法看到这些请求。需要在迁移入口的同时收紧源站访问，必要时配合更换已暴露地址。不要为了临时排障把所有端口向公网开放，否则恢复业务的动作可能增加新的入口。

## 清理攻击之后留下的积压

新请求被挡住后，已有慢查询、排队任务和失败重试仍可能继续消耗资源。应由应用负责人决定哪些任务可取消、哪些写入必须确认结果。盲目重启可能中断重要事务或造成重复操作。恢复确认应包括真实用户功能，而不是只有服务器能被探测到。

## 判断“被打”之前，排除发布与依赖故障

将异常开始时间与最近部署、定时任务和数据库变更对照。一次错误发布也可能让请求重复失败，客户端不断重试后，流量看起来像攻击。没有证据时先描述现象，不急着把故障归因于某个攻击者。排查方向正确，才不会在错误产品上继续加预算。

主机指标要结合业务看。CPU 不高但请求超时，可能是连接池、磁盘或外部服务等待；连接数增加也可能由应用没有及时关闭造成。检查代表性请求的时间分布，找出从什么时候开始排队。安全防护和应用修复可以同时推进，但不能互相替代。

## 按服务类型选择保护入口

网站的 HTTP 请求可以经过网站 CDN，数据库管理端口不应因此直接公开；游戏与自定义协议需要对应代理或清洗服务。列出每个公网端口的用途与负责人，停用无必要的服务。减少可攻击入口，有时比增加一层复杂规则更直接。

CDN5 官网分别提供高防 CDN、高防 IP 和游戏 SDK 盾。咨询时明确是网站、接口还是非网站通信，要求对应方案说明正常业务带宽与协议范围。不要将某个产品的防御数字写进另一个产品的采购要求，造成双方对保障对象的理解不同。

## 控制进入源站的请求，而不是只换域名

如果攻击者知道旧 IP，可以继续直接发送流量。接入 CDN 的同时，核对防火墙与源站认证，允许必要回源和管理通道，拒绝未授权访问。已经暴露的地址是否更换，应结合机房状态和迁移成本决定，更换后仍要关闭原暴露路径。

检查图片、下载、测试与管理子域名是否仍指向同一源站。服务器主动请求外部资源的出口也值得关注。地址隐藏不应建立在别人永远查不到的假设上；即使地址被知道，业务入口仍应有明确访问限制。

## 服务器恢复后，不要立刻把限制全部撤掉

排队请求、自动任务和客户端重试可能继续产生压力。先观察当前负载，恢复重要功能，再逐步开放非必要操作。对耗时任务设置执行数量与取消条件，对数据库中的异常长任务由应用负责人确认是否结束，避免中断关键事务。

如果需要重启，先明确恢复依赖与数据状态。重启可以清理部分进程状态，也可能让缓存全部失效，形成额外回源和查询。没有准备的连续重启，容易使系统一直停留在启动和预热阶段。记录每一步的目的与结果，减少凭感觉操作。

## 限流维度应该跟着业务走
按来源地址限流部署简单，但企业代理和移动网络可能让许多用户共用出口。对登录接口，可以结合账号与来源控制失败尝试；对搜索接口，可以按会话、查询成本和时间窗口限制；对开放 API，应考虑调用方凭证及合同额度。不同接口的身份条件不一样，不适合用一条规则全部覆盖。

限流还要明确超过阈值后的动作。直接拒绝、延迟处理、要求额外验证或进入排队，对用户体验与资源占用的影响不同。网页可以展示验证步骤，机器接口通常需要清晰的错误响应与重试指引。让 API 收到一段网页验证码内容，会使客户端难以判断发生了什么。

请求速率和并发请求也要分开。一个客户端发送速率不高，但每次请求长时间占用资源，仍可能造成连接积压。对耗时任务可以限制同时执行数量，采用异步任务与结果查询，并给任务设定取消和超时条件。边缘限制与应用执行限制配合，才能控制真正的处理成本。

## 配置变更要能够解释和撤回

缓存、证书、回源和安全规则都可能影响整站访问。保存变更之前，应保留原配置与修改原因，并明确验证步骤。对影响较大的规则，先在测试域名或有限路径使用，观察结果后再扩大范围，能降低一次错误波及全部业务的概率。

操作权限应按职责划分，日常查看数据不需要同时拥有修改域名与密钥的能力。对自动化任务使用独立凭证和必要范围，避免多人共享长期高权限账号。人员或系统退出时，应及时撤销相应权限并检查遗留任务。

回滚也需要验证。记录恢复到哪一版本、哪些缓存或连接状态不会立即恢复，以及谁负责确认业务可用。控制台显示配置已保存，只能证明操作提交成功，不能代替真实请求的检查。

## 正常高峰与攻击要使用不同的处理方法

真实用户集中访问时，排队、缓存和业务降级可能比大量封禁更合适。恶意请求则应根据行为和资源成本处理。识别不确定的流量可以先限速或观察，确认误报影响再扩大拦截。共享出口的企业或移动用户尤其容易受单 IP 阈值影响。

对登录与支付等操作，需要业务成功率作为反馈。请求数量下降，可能是攻击被控制，也可能是客户被挡在门外。把拦截日志和正常操作结果关联，才能判断防护是否达到目的，而不是仅让监控曲线变平。

## 给下一次扩容留下可靠依据

保存攻击期间峰值、持续时间、受影响路径和源站资源变化。没有准确数据时，可以保留区间和观察限制，不必为了询价补出精确数字。与 CDN5 讨论升级时，说明瓶颈发生在带宽、连接还是应用层，让资源投入对准真正问题。

长期维护还需要定期更新系统和依赖、检查权限及验证备份恢复。CDN 能减少部分恶意流量进入源站，但不会替你修复应用缺陷。把网络防护与应用运维分清职责，才能避免每次故障都只剩下换服务器这一种选择。
